# evolve — context for Claude

A set of utilities to facilitate designing **game characters, scenes, LoRA
adaptors, and identity-preserving transforms** for Ren'Py games, by driving
ComfyUI entirely through its HTTP API — the ComfyUI UI is not part of the
loop. This file carries everything learned building the pipeline, so a fresh
session starts fully up to speed.

## Vocabulary (user's ontology, 2026-08-19 — use these terms)

The unifying idea: ALL image work here is **evolution through selective
breeding with auditable heredity**. One engine (evolve.py), typed
promotion on top. The user's four apparent tools (char creation, char
imagery, arbitrary images, image modification) differ only in spawn-time
constraints and promotion target, not mechanism.

- **CHAR** — a humanoid game actor: consistent appearance; compositable
  (transparent); posable; expressive; multi-viewpoint/lighting.
- **SCENE** — like a movie scene: consistent appearance,
  multi-viewpoint/lighting.
- **IMAGE** — a rendering of a char, scene, or composition.
- **GAME-IMAGE** — an image promoted to game-asset status.
- **SPAWNED image** — from a prompt + 1–4 reference images = **PARENTS**.
- **FIAT image** — "let there be": prompt + empty latent (gen 0).
  **EVE/ADAM** — fiat images founding a female/male char. Every image's
  oldest ancestor is a fiat image.
- **Kinship (REDEFINED 2026-08-23, overrides everything earlier):**
  **PARENT** = a reference image. **CHILD** = an image that used this image
  as an input. **SIBLINGS** = images generated by an IDENTICAL config
  MODULO SEED — recipe minus seed (and seed-derived noise) plus the parent
  id list. Confirmed by the user ("that's exactly what I meant"): captures
  lock/vary/lora+strength/steps/cfg/family/w/h/white-bg, so a re-roll with
  any knob changed is NOT a sibling. Imports are singleton sibling sets.
  The older keys are RETIRED: "same parents + same prompt text"
  (2026-08-22) and "one Generate round" both approximate this and lose to
  it. Re-rolls of an unchanged config still merge — the button press was
  never the boundary. The FATHER/BROOD/DECK vocabulary (prompt-as-father,
  fanned card decks) is dead with the walker UI; mother = parent 0 remains
  a DATA term (slot 0, restored to ref0 on pick), no longer a UI concept.
- **BREEDING** — user picks up to 4 parents + prompt → spawn children.
- **BUDDING** — single-parent breeding; the standard way to POSE a char,
  relight a scene, etc.
- **Lineage rule (doctrine):** heredity is a tree with a DAG overlay —
  parent 0 (the "mother", slot 0, tree-image-only) is the CONTINUITY
  CARRIER and defines the filesystem path; co-parents (slots 1–3) are
  meta-recorded edges only.

## Identity transfer — node knowledge

- Use **`IdentityFeatureTransferFinal`** (in the Enhancer pack's
  `identity_feature_transfer.py`). The older V3 exists only for compatibility
  with the user's downloaded template workflows (myaiforce "F2K Identity
  Transfer" single/multi reference — kept as comparison baselines).
- Final's presets are pure similarity gates — block schedules are identical
  across presets; only `similarity_floor`/`softmax_temperature` differ:
  SOFT 0.5/0.07, MID 0.2/0.07, HARD 0.04/0.025. `custom` allows sweeping the
  floor continuously if a character holds identity poorly.
- **SOFT_LOCK is the proven default** (user-verified repeatedly): identity
  holds while pose/camera stay free. Hard locks anchor composition to the
  reference framing. When dialing in a new shot/character, render all three
  presets on ONE seed and let the user pick.
- Refs enter as `ReferenceLatent` chains (core nodes) in BOTH positive and
  negative conditioning. `reference_index`/`reference_indices` on the Final
  node select which refs drive IDENTITY; all refs steer composition
  regardless. Convention: first ref = primary identity (`reference_index` 0).
  Final also supports per-reference subject masks (1–8) — the future route to
  two characters in one CG without feature bleed — and optional sigma-decay.
- Identity transfer is style-agnostic feature matching on VAE latents (not a
  face model): references in any style work, but the OUTPUT is rendered in
  Klein's style. Plan for original characters: design in Illustrious → one
  Klein pass → approved **Klein-native master reference** per character → all
  subsequent renders reference the master. Never mix raw Illustrious renders
  with Klein output in one game (style drift).

## Driving the API — patterns

- Payloads are API-format JSON: `{"client_id": ..., "prompt": {node_id:
  {class_type, inputs}}}` to `POST /prompt`; poll `GET /history/<prompt_id>`
  until the id appears; output filenames are in `outputs.<node>.images`;
  files land in `D:\projects\ComfyUI\output\<subfolder>`. Input images must
  be staged into `D:\projects\ComfyUI\input\` first.
- Node-id vocabulary used across all templates/scripts: `unet clip vae img_i
  enc_i txt zero pos_i neg_i ift guider sampler sched noise latent samp dec
  save` (+ `msk lat` in inpaint graphs, `split` for partial denoise).
- Sampling: euler via `KSamplerSelect` + `Flux2Scheduler` (4 steps) + 
  `CFGGuider` cfg 1.0 + `SamplerCustomAdvanced`; negative = 
  `ConditioningZeroOut` of the prompt, ref-chained like the positive.
- API-format JSON opened in the ComfyUI UI shows an EMPTY canvas (no node
  geometry — a silent no-op). `add_geometry.py` (adopted from
  `..\charmed_pipeline\api_to_ui.py`) converts any payload into a loadable graph: topological auto-layout, with exact
  socket/widget definitions fetched from the live server's
  `/object_info/<class>` (widget vs socket: combo lists and INT/FLOAT/STRING/
  BOOLEAN are widgets; `control_after_generate` inputs get an extra "fixed"
  widget value).
- Process lessons: write Python drivers as FILES and run them (long inline
  `python -c` in PowerShell trips quoting and command filters); guard scripts
  with `if __name__ == "__main__":` — importing a helper from a script whose
  queue/poll code is module-level re-runs the whole batch.

## Matting / finalize

- `finalize.py`: **rembg + isnet-anime** (user-verified better than
  InSPyReNet/`transparent_background`, which missed an enclosed white pocket
  in hair — both are installed). First isnet-anime use downloads ~176MB to
  `~/.u2net` (already cached). ~5s/image warm.
- Raw mattes from BOTH tools leave character interiors at alpha 240–254
  (~2–5% translucent → ghosting over dark scenes). Fix: harden the matte
  (≤40→0, ≥220→255, linear stretch between) — keeps anti-aliased edges,
  matches game-sprite near-binary alpha.
- Default is now IN-PLACE matting: the webp keeps the render's exact dims
  and character position (variants drop in beside the ref sprite).
  `normalize=True` / CLI `--normalize` is the legacy deliverable path: trim
  to alpha bbox → scale to 1080 height → center on a 1920x1080 canvas.
  Output is webp (quality 95). ALWAYS write and inspect the
  `_darkcheck.png` (composite over dark charcoal): white-halo/pocket/edge
  failures are invisible on light backgrounds.
- **Generate on a solid WHITE background, never black** — matting dark
  clothing off black fails; "black background" requests are delivered as
  transparent sprites instead.
- **Never feed alpha-bearing refs raw**: LoadImage drops alpha, the model
  sees a cutout and paints checkerboard "transparency" blocks around the
  character (seen live with a Charmed sprite ref). `pose_from_char.py`
  auto-flattens transparent refs onto white AND prefixes the prompt with
  "Solid plain white background." (both gated by `--flatten-alpha`,
  default on).
- The legacy trim+scale normalization makes separately-generated sprites of
  the same character converge to near-identical geometry (verified: a full
  re-render's face landed on the same image-point as the inpainted
  variants'). In-place matting achieves the same via the ref anchoring
  composition.

## Hard-won generation learnings (the rock-paper-scissors campaign)

Getting a specific hand gesture (or any precise pose detail) onto a character
— the full failure ladder, so it is never re-climbed:

1. **Winner: full re-render with an orientation-matched gesture crop as a
   secondary reference**, identity pinned to the primary (`--identity-refs 0`
   conceptually; "all" also worked since the crop was the same character's
   hand). Crop a clean instance of the gesture — best source is an earlier
   render of the same character in the same style, even a failed one —
   **mirror/rotate it into the exact target orientation first** (the model
   copies orientation with shape; it will not mentally rotate a reference),
   place it on white, clean stray non-white fragments from the crop (they
   teach the model to grow hair/objects). Then seed-sweep; hit rate ~2/8.
2. Prompt-only gesture requests: 0/9. The model satisfies "hand" and
   "gesture" separately (parks the gesture in genre-prior locations like
   raised-beside-the-shoulder), and confuses gesture vocabulary (scissors →
   devil horns). Naming the gesture first and describing both hands helps but
   does not fix it.
3. Masked inpainting (`SetLatentNoiseMask` on a feathered mask, full-strength
   sigmas) is EXCELLENT for small local variants — rock and paper gestures
   landed in one round when the hand only needed re-posing in place — but bad
   at inventing structure: generous masks grow phantom extra hands, tight
   masks make the hand vanish (the laziest valid completion). Locate mask
   coordinates by cropping the source image and looking at it.
4. Variant sets made by inpainting one base share the frozen latent outside
   the mask: outputs differ by max 4–6/255 there (VAE decode ripple at the
   feathered boundary) — visually identical, flip cleanly in-game. For
   bit-identical, composite the masked region back onto the base PNG before
   matting (**offered, not yet implemented**).
5. Paste-then-refine (composite gesture pixels, partial denoise via
   `SplitSigmas` low half on an 8-step schedule): denoise ≤0.5 barely touches
   the paste (halo survives); 0.6–0.75 blends edges and adds detail but
   struggles to bridge anatomy (floating wrist/cuff gaps); a follow-up
   junction-only full-denoise pass connected it but degraded the gesture.
   Erode+blur the paste alpha to kill white fringe before refining. The user
   rejected this route — and per-image manual touch-up doesn't scale.
6. Secondary refs pull their subject INTO the composition: a hand ref made
   extra hands appear elsewhere in ~5/8 renders; "her other hand is not
   visible" phrasing does not reliably suppress it. Pre-screen and reject.
7. **Seed dominates lock level** for detail quality — SOFT vs MID changed
   hands very little; the seed changed everything. Sweep seeds, not knobs.
8. Camera moves: LEAD the prompt with the camera instruction and describe its
   visual consequences ("her knees large in the foreground, the underside of
   her jaw visible"); a kept seed anchors the old composition — use a fresh
   one. Burying "low angle" mid-prompt does nothing.
9. Reproduction prompts: describe the character fully (hair, eyes, outfit
   piece by piece) even though refs are attached, then state "The only
   change: ...". Femininity/nails drift on hands unless stated ("slender
   feminine hand, pink nail polish").

## Viewpoint control — the Qwen multi-angle campaign (2026-08-22)

Testing `qwen-image-edit-2511-multiple-angles-lora` (fal, Apache 2.0, already
installed) as the engine for a **`[VP: ...]` budding operator** in evolve.
Trained grammar is a closed 8x4x3 enum:

    <sks> <azimuth> <elevation> <distance>
    azimuth   (8): front / front-right quarter / right side / back-right quarter
                   / back / back-left quarter / left side / front-left quarter
    elevation (4): low-angle (-30) / eye-level (0) / elevated (30) / high-angle (60)
    distance  (3): close-up (x0.6) / medium shot (x1.0) / wide shot (x1.8)

`distance` scales ORBIT RADIUS, not crop — so this is a camera
parameterization, i.e. BUDDING (single parent, parent 0 carries continuity),
NOT a model family. Driver: `qwen_vp_probe.py`.

1. **THE CENTRAL FINDING — it cannot distinguish "orbit the camera" from
   "turn the subject."** It was trained on Gaussian-splat *turntable* renders,
   where those two produce pixel-identical sequences. The model was never
   given a signal separating them, so it satisfies a viewpoint request by
   either route. Verified live: `01376 back` turned the woman 180 to face the
   wall with the camera completely stationary; `02504 right` did a genuine
   orbit with her pose preserved.
2. **Background IS the camera channel** — and the chirality channel too
   (finding 5). Rotation can only be *expressed* through background
   parallax, so scene richness decides which reading wins.
   Bar interior (perspective lines, counter, ceiling) → real orbits. Flat
   wall → mostly subject-turn, though at 135 it *invented a wall corner* to
   justify a camera move. Featureless grey → orbit isn't expressible at all,
   everything reads as subject rotation. User confirms this holds across
   other transforms they have attempted.
3. **Given no subject, it nominates one.** On an empty bar plate (303.png) it
   picked the nearest stool and orbited *that*, and sometimes rotated the
   stool instead — furniture changing orientation between renders.
4. **THE AZIMUTH TOKEN IS A RELATIVE ROTATION, NOT AN ABSOLUTE POSITION**
   (settled 2026-08-22 by the 32-render sweep, 8 azimuths x 4 seeds on
   02504, with the user's plan-view measurements). **Seed does not move the
   viewpoint** — pose and detail only. Two earlier readings are RETRACTED:
   "a distribution to sample" (wrong — the mapping is stable) and "direction
   never changes / a ~80-degree arc" (an artifact of only ever sampling the
   right hemisphere).
   Measure the VIEW ANGLE `cp - gf` (camera bearing minus the subject's
   facing) — that is the only quantity the model represents. Plan view,
   girl at origin, camera always facing her, r~1.5m; original cp 225,
   gf 180, so the source view angle is already 45.

       token         nominal   cp   gf     cp-gf   delivered   gain
       front              0   225  180        45      0        exact
       front-right      +45   260  180        80    +35        0.78
       right            +90   285  180       105    +60        0.67
       back-right      +135   337  180       157   +112        0.83
       back            +-180  300   90       210   +165        0.92
       back-left       -135   160  225       295   -110        0.81
       left             -90   180  225       315    -90        exact
       front-left       -45   225  180        45      0        FAILED

   - `front` = identity is the decisive case: an ABSOLUTE reading would put
     the camera at her front (cp 180); it did not move, because a relative
     rotation of 0 is no change.
   - **Handedness DOES work**: right-family positive, left-family negative,
     `left` exact at -90.
   - **Magnitude under-delivers, gain ~0.8** — a correctable scale factor.
     Compensate by requesting ~1.25x the wanted rotation.
   - **The camera/subject split follows one rule: move the CAMERA where
     there is visual evidence; rotate the SUBJECT where a camera move would
     require inventing unseen space.** Every case that recruited girl-
     rotation (`back`, `back-left`, `left`) needed the camera to swing LEFT,
     toward and behind the bar — the back-bar side, absent from the source.
     Rightward moves stayed pure camera out to +112. `front-left` (-45)
     refused to move at all rather than reveal a sliver of that same space.
   - That rule unifies the whole campaign: a figure gets full 360 (turning a
     person is generation); a room gets a limited arc (orbiting it means
     inventing walls); an empty plate gets a nominated stool (it needs
     SOMETHING rotatable). Finding 1 restated precisely: it is not confusion
     between camera and subject — only the relative angle is represented,
     so the split is free and it picks whichever is cheaper to render.
   - **Design consequence for `[VP: ...]`: a RELATIVE rotation control with
     ~1.25x gain compensation, not an absolute pose picker.** To reach an
     absolute pose, chain steps and re-measure. Expect refusals in the
     direction of unseen space — the fix is to give the model that space
     (a wider or differently-framed source), not a bigger number.
5. **BACKGROUND ALSO CARRIES CHIRALITY — the same channel, a second job.**
   Handedness works when there is scene geometry (02504: right-family
   positive, left-family negative, `left` exact) and COLLAPSES without it.
   On plain white (311) the model "failed to distinguish front-left from
   front-right" (user, 2026-08-22); on plain grey (02488) handedness was
   inconsistent within one set — `front-right` showed her right side,
   `back-right` her left. Cause: a near-symmetric front-on figure on a
   blank field is nearly its own mirror image, so +45 and -45 are
   indistinguishable and nothing prefers either. Only the scene fixes
   chirality.
   **Practical rule:** on plain backgrounds use ONE hemisphere and accept
   mirror ambiguity, or plant an asymmetric cue (prop, asymmetric hair or
   clothing, a directional shadow) to break the symmetry.
6. **90 (exact profile) is the weak spot, for the same reason.** `02488
   right` produced a smeared torso plus a caption strip in MIRROR-REVERSED
   text — the model pulling toward a mirrored render. Plain grey, symmetric
   bust, maximal left/right ambiguity: it failed to commit. The mirrored
   lettering is the tell that this is chirality collapse, not general
   breakdown.
7. **135 undershoots to ~90** (`02488 back-right` gave a clean profile).
8. **LIGHTNING BEATS THE SLOW PATH — on quality, not just speed** (user
   verdict: "BETTER in all cases"). Stack
   `Qwen-Image-Edit-2511-Lightning-4steps` after the angle LoRA: 4 steps /
   cfg 1.0 vs 20 / cfg 2.5. **83s -> 13s (6.4x)**. Why quality improves: this
   is an EDIT task, and 20 steps at cfg 2.5 gives the model room to invent;
   fewer steps at cfg 1.0 stay closer to the source, which is the whole job.
   THE SETTLED RECIPE. Generalize the principle to other edit-type work.
9. **Consequence for the composite route** (user's plan: turn figure and
   background independently, composite, so "she turns" becomes "we orbit"):
   the FIGURE half is viable — subject rotation on a plain background is
   exactly what this tool is good at, ~13s a pose. The PLATE half is NOT:
   you cannot get a stable room re-viewed at a chosen angle. That half needs
   a GEOMETRY-CONDITIONED method — MetaView (Qwen-Image-Edit + Depth
   Anything 3) or ViewCrafter (point cloud) — which never has to nominate a
   subject because depth tells it what the room is. Compositing constraints:
   camera height must match the elevation token, orbit radius changes
   perspective compression (not just scale), light direction must agree
   (encouragingly it re-derives shadows self-consistently), and matting
   yields no contact shadow. A finishing **Klein IFT pass over the
   composite** harmonizes seam, lighting and contact shadow while
   canonicalizing style — rough composite as a steering reference.
10. Check `lora key not loaded` after every new LoRA (standing rule): the
    angle LoRA and the Lightning stack both loaded 100% — unlike the Klein
    key-name bug, this is a different arch and needs no fixup.
11. **THE PIVOT IS THE SUBJECT, NOT THE ROOM** — measured, not inferred
    (338, the three-frame test: oblique room, oblique body axis, camera
    agreeing with neither, so "rotate about the subject" and "rotate about
    the scene" finally made different predictions). The model pivoted on the
    girl and **made no major pose changes**; the room did not rotate
    coherently — 7 of 8 lost her diagonality, collapsing toward a more
    canonical framing. Only `front-right` (the SMALLEST positive step,
    ~+35 delivered) held the oblique geometry and produced a genuine
    front-on-to-her view of an oblique scene.
12. **BACKGROUND LEGIBILITY HAS A SWEET SPOT — clutter is as bad as blank.**
    Too little (311 white, 02488 grey): no camera channel, chirality
    collapses. Too much (338's dense bedroom): the model cannot track it,
    abandons it, re-generates it, and falls back to the figure. 02504's bar
    was the sweet spot — strong, SIMPLE, legible perspective (counter line,
    ceiling, backbar) without overwhelming detail. So for scene work,
    generate location plates with LEGIBLE geometry (clean planes, strong
    lines), not maximal detail.
    Corollary — the model preserves whatever it treats as the subject and
    spends its budget re-inventing the rest: a legible room gets kept and
    the SUBJECT may be re-posed (02504's girl rotated on her stool); an
    illegible room gets abandoned and the SUBJECT is preserved (338).
13. **PRACTICAL ENVELOPE: about one quarter-turn.** The scene-preserving
    successes are all modest moves; large requests degrade geometry.
    `[VP: ...]` should offer +-1 step as reliable and treat anything beyond
    as speculative — chain steps rather than asking for a big rotation.
14. **ELEVATION AND DISTANCE WORK — and are the useful axes** (tested
    2026-08-22, full 4x3 grids at azimuth `front` on 311 figure-on-white,
    315 figure-in-dense-bedroom, 02504 bar figure; user verdict "much more
    satisfactory than azimuth control", 👌🏻).
    - **`eye-level` + `medium shot` is ~IDENTITY**, so these axes are
      RELATIVE like azimuth. Consequence for UI: a "(no change)" option is
      not a special case needing branch logic — it is simply the neutral
      token, and "both neutral" is the identity transform.
    - **Distance genuinely DOLLIES** — it changes perspective compression,
      not just framing, exactly as the orbit-radius multipliers
      (x0.6/x1.0/x1.8) imply. It is not a zoom or a crop.
    - **Why this axis beats azimuth, twice over.** (a) No chirality to
      collapse: up and down are not mirror-ambiguous, which is precisely
      what killed azimuth on plain backgrounds (finding 5). (b) There is no
      alternative route to camera height — Flux ignores camera-height
      instructions in the prompt, whereas a different azimuth can simply be
      generated fresh. So this control has no substitute; azimuth does.
    - Elevation has FOUR trained values (low -30 / eye 0 / elevated +30 /
      high +60); distance has three. `high` is the least explored.
    - RETRACTED 2026-08-23 (user's chained experiments in evolve): the
      tokens SET an ABSOLUTE camera spec in the subject's frame - they do
      not delta it. "close-up" on an already-close image is a NO-OP. The
      earlier "relative + identity at eye/medium" reading was a confound:
      every probe source was already ~eye-level medium, where absolute
      targeting and relative-with-neutral-identity are indistinguishable.
      Consequences: trained names are the labels (comparative labels were
      wrong); "(no change)" is not a token - leaving an axis alone means
      OMITTING its token (partial grammars untested); idempotent re-runs =
      more takes of the same camera.

## Tags doctrine, settled 2026-08-25 (after building v1)

**"Don't go crazy with tags unless they make the code more maintainable;
keep them as a layer on top of some fixed rules."** (user). Tags are
COLLECTIONS the user curates. The code may READ two of them because they
are collections with consequences - `pinned` (the keep pile: sweep and
prune skip it) and `lora_dataset_<name>` (a LoRA's dataset) - and owns
none. **`archived` is a BIT, not a word** (record flag, `archive` /
`restore` journal events, like `purged`): it is read everywhere (views,
garbage, sync, sweep, prune) and never behaves like a category, so it was
a state flag in a tag costume. `archived` is a RESERVED word (rejected by
`clean_tags`). Rule: pinned => not archived - `pin()` restores,
`archive()` SKIPS pinned images unless `force` (which unpins them);
discard on a pinned image refuses ("kept: pinned"). UI: archived images
are hidden from every view unless the word-bar toggle "show archived" is
on; the `trash` chip is the view of exactly the archived; the Info popup
has an `archived` checkbox (force) + the gc verdict. Legacy journals with
the word are translated on load. `/api/archive {id|ids, on, force}`.
Derived words (`cam:low`, `fam:klein`) are a future rendering of recipe
facts - computed, never stored, never typed by hand ("if the system can
compute it, the user never types it").

**Drop-into-view (agreed, NOT BUILT):** a view is a single word;
dropping an image into it adds the word, Del removes it; drops never
cascade; multi-word/boolean views are browsing-only ("You can't drop this
item into a view - see Set Theory"); the relational Genealogy sheets and
derived-word views are never drop targets. Dragging a view chip onto a
view adds the word to every member.

## Model family & validation — BUILT 2026-08-25

`model_family.py` is the ONE definition of the closed model set:
`ModelFamily` (str Enum: klein / zimage / illustrious), `ModelFamilyInfo`
(label, steps, cfg, references, lora, trainable), `parse_model_family()`
(the single validator), `model_families_for_ui()`. Nothing else may spell

enum values). Configs are **pydantic** models, validated at the HTTP edge
(a `ValidationError` -> one readable 400 via `api.invalid()`):

`CameraConfig` (axis tokens validated against the vocab, >=1 axis),

    just a subdir (`<root>/<project>/images/NNN.png` + journal.jsonl +
    state.json + archive/); create/select/switch IN-APP, and its total and
    single effect is the path context (state/journal swap because those
    files live under the path). Ids are per-project; `<project>/<id>` is
    the global image name. `<root>/config.json` = the app-level config

    _train. Migration = manually move an old store dir under the root as a
    project subdir (same volume: staging hardlinks survive).
  - **Asset:** an entry in `<root>/assets.json`:
    `{name, loras: [paths], dataset: [{path, description}]}`. The LIST is
    the asset - images live wherever they live (any project), dragging
    into the asset view adds an entry, Del removes it. `description` IS
    the training caption (per-entry, seeded `name + ", " + recipe prompt`,
    trigger-prefix validated; name IS the trigger, never auto-decorated).

    like every root; closure covers images only, never RNG/temp).
